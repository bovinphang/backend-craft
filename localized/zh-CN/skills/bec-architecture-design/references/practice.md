# 后端架构设计

## 关键检查

1. 先读真实模块、调用链、部署约束和归属，再提拓扑；用证据记录现有不变量及痛点。

2. 明确业务能力和数据归属，让模块边界的依赖方向与公共契约易于理解。

3. 以变更频率、故障隔离和运维成本比较最小可行方案；能满足目标时保留现有单体。

4. 说明一致性单元、重试、消息投递、超时预算和恢复归属；图示不能代替失败语义。

5. 规划可逆迁移切片和兼容边界，区分假设与已核实约束，指出需要产品决定的事项。

6. 交付 ADR：问题、备选、决策、证据、后果与验证；关系需要图示时复用公共图表工具。

<a id="scope"></a>
## 边界与案例

适用场景：
- 为现有后端划定模块边界
- 比较模块化单体与服务拆分
- 明确数据所有权和故障边界
- 编写包含迁移回滚的架构决策

相邻专项应按实际任务选择；纯前端 UI、图片生成和普通文案润色不在此范围。

## 交付要求

- 已读取的工程/契约证据及变更作用域。
- 选用方案、关键不变量、资源/错误或失败边界。
- 实际运行的命令与结果，未运行项及不能证明的结论。
- 兼容、恢复/回滚或后续处理限制；评审结论须给可核实位置。

## Java 服务领域边界

Java 服务的应用、传输与持久化边界遵循真实部署和业务一致性单元；不把服务分层强加给 Java 库或桌面模块。
