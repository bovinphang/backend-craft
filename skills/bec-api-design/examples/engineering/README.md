# HTTP replay after response failure — EP-SVC-01

Use Go >=1.20 with the standard library only. Run `go test -json -count=1 .` from this directory. Set `CRAFT_ENGINEERING_DEFECTIVE=1` to remove deduplication and observe three real assertion failures, then `0` for the protected default. From the product root, `pnpm run verify:engineering` compiles and runs both variants from an isolated source copy, preserving raw JSON test logs and hashes under reports/engineering. No dependencies are downloaded; `--prepare` is accepted but not needed for this standard-library case.

Real httptest HTTP clients observe commit followed by a failed 503 response, replay of the same key and canonical intent with the same receipt and one injected effect, 409 rejection for changed intent, and concurrent duplicate results with one effect. The injected effect increments an atomic counter; it is observed independently of HTTP response generation. Different JSON property order does not change the decoded business intent. There is no arbitrary sleep for ordering.

This is a single-process, in-memory example. A mutex protects effect/result ownership; records are retained for the test lifetime. Production requires the actual durable atomicity, retention, capacity and recovery design. There is no database, message broker, crash recovery or distributed exactly-once proof. The principal callback in tests returns a synthetic constant: it is not authentication and no role header is trusted. The status codes are this sample's contract. Retry only the same operation/key/intent under a bounded budget and verified server replay contract; a timeout or generic 5xx alone does not authorize arbitrary write replay.
